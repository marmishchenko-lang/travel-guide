# Інтеграція зон безпеки з DeepState — реальний, робочий код

## Що змінилось порівняно з попереднім планом

Спочатку план був: отримати офіційний ліцензований API-доступ від DeepState напряму.

Тепер — **краще рішення, знайдене і перевірене**: репозиторій
[`cyterat/deepstate-map-data`](https://github.com/cyterat/deepstate-map-data)
щодня (о ~03:00 UTC) автоматично забирає геометрію окупованої території з
DeepState Map через GitHub Actions і публікує її як звичайний публічний
GeoJSON-файл. **Жодної ліцензії, жодного ключа, жодних перемовин не
потрібно** — це публічні дані.

Я перевірив це напряму (не з чужих слів): склонував репозиторій,
відкрив `data/deepstatemap_data_20260814.geojson`, підтвердив структуру
і прогнав реальну класифікацію на 17 містах. Працює. Результати нижче.

## Реальна структура даних (перевірено, не припущення)

```json
{
  "type": "FeatureCollection",
  "features": [{
    "type": "Feature",
    "properties": {},
    "geometry": { "type": "MultiPolygon", "coordinates": [ ... ] }
  }]
}
```

Один `MultiPolygon` = уся тимчасово окупована територія. Окремої лінії
фронту (LineString) в цьому джерелі немає — "відстань до лінії фронту"
рахується як відстань до **межі** цього полігону.

## ⚠️ Важливе застереження — прочитайте перед запуском

Відстань рахується **по прямій (геодезично)**, а не по дорогах. Для
більшості міст це нормально, але для прибережних/приморських міст
(Одеса, Миколаїв) пряма лінія до найближчої точки окупованої території
може йти **через море**, і виходить коротшою за реальний безпечний
сухопутний маршрут. Саме тому Одеса вийшла "червоною" при 61 км —
це, ймовірно, не відповідає реальному ризику для сухопутної поїздки.

**Що з цим робити:** механізм ручного перевизначення (`data/overrides.json`)
існує саме для таких випадків. Перед запуском Фокальній точці з безпеки
варто переглянути результат по всіх містах (таблиця вище — гарний
стартовий чекліст) і зафіксувати вручну ті, де пряма відстань вводить
в оману. Це не баг коду — це властивість "відстані по прямій" як методу,
і жодна автоматика тут не замінить погляд людини, яка знає реальну
географію доріг.

## Структура файлів

```
deepstate-integration/
├── netlify.toml                        # конфіг Netlify Functions
├── package.json                        # залежності (@turf/turf, @netlify/blobs)
├── data/
│   ├── cities.json                     # довідник міст для dropdown (додавайте сюди нові)
│   └── overrides.json                  # ручні перевизначення зон
├── shared/
│   └── classify.js                     # логіка класифікації (перевірена, працює)
├── netlify/functions/
│   ├── update-zone-cache.js            # SCHEDULED — тягне дані, рахує зони, кешує
│   └── get-city-zones.js               # GET — віддає кеш фронтенду
└── public/js/
    └── zone-dropdown.js                # dropdown-віджет для travel_application.html
```

## Як розгорнути (без розробника — кроки для будь-кого з доступом до Netlify)

1. Скопіювати папки `netlify/`, `shared/`, `data/`, `public/` у корінь
   вашого існуючого Netlify-проєкту (того самого, де вже лежить
   `true-travel-dashboard`).
2. Додати залежності з `package.json` (`npm install`) або просто
   переконатись, що Netlify підхопить їх з `package.json` при білді.
3. **Жодних Environment Variables не потрібно** — джерело публічне.
4. Задеплоїти (`git push` — Netlify збілдить автоматично).
5. Перевірити вручну: відкрити
   `https://ваш-сайт.netlify.app/.netlify/functions/update-zone-cache`
   один раз у браузері — це примусово наповнить кеш одразу, не чекаючи
   першого спрацювання за розкладом (кожні 6 год).
6. Перевірити `https://ваш-сайт.netlify.app/.netlify/functions/get-city-zones`
   — має віддати JSON зі списком міст і зонами.

## Як підключити dropdown у travel_application.html

1. У розмітці, поруч із існуючим полем `#req-place` (рядок ~465),
   додати: `<div id="zone-city-picker"></div>`
2. Перед `</body>` додати:
   `<script src="/js/zone-dropdown.js" defer></script>`
3. Все. Dropdown сам підтягне список міст і зони з кешу.

## Що лишається "фазою 2" (не блокує запуск)

- **Власне дзеркало репозиторію** (як пропонувалось: свій GitHub repo +
  Actions замість прямого читання з `cyterat/...`) — розумна ідея для
  довгострокової стабільності (незалежність від того, чи автор
  підтримуватиме репозиторій), але не обов'язкова для старту.
- **Історичні дані / порівняння дат** — у джерелі вони вже є
  (`deepstate-map-data.geojson.gz` з датами), можна додати пізніше
  для аналітики "як змінювались зони за місяць", не потрібно зараз.
- **Розрахунок по дорогах, а не по прямій** — усунуло б проблему
  з Одесою/Миколаєвом, але це вже окремий, значно складніший проєкт
  (потрібен роутинг-сервіс на кшталт OSRM). Для старту — ручне
  перевизначення дешевше й швидше.
